# SCOPE-R — Платформа мониторинга стоимости путешествий

## 0. Назначение документа

Документ является техническим заданием на разработку MVP аналитической системы **«Платформа мониторинга стоимости путешествий»** (`Travel Cost Observatory`).

Система предназначена для регулярного сбора рыночных предложений по транспорту и проживанию, нормализации данных, расчета **расчетной типовой стоимости путешествия**, накопления исторических снимков рынка и визуального анализа динамики стоимости по выбранным туристическим сценариям.

Документ рассчитан на передачу AI coding-agent, backend/data engineer, full-stack разработчику, системному аналитику и архитектору.

# S — Scope

## 1. Цель MVP

За 6 недель реализовать работающий прототип, который:

- ежедневно пересчитывает не менее 100 активных туристических сценариев;
- охватывает 6 городов: Москва, Санкт-Петербург, Краснодар, Сочи, Калининград, Южно-Сахалинск;
- использует минимум 2 подтвержденных источника транспортных данных;
- использует минимум 2 подтвержденных источника данных по проживанию;
- поддерживает автоматический мониторинг и расчет пользовательского сценария по запросу;
- сохраняет raw-ответы, нормализованные предложения и исторические снимки рынка;
- показывает динамику стоимости, структуру стоимости, диапазон P25–P75 и качество данных;
- экспортирует выбранные данные в CSV и Excel;
- содержит экран контроля источников и качества данных.

## 2. Основной бизнес-результат

Система не определяет «истинную цену», не рассчитывает фактический средний чек и не анализирует реальные транзакции туристов.

Система рассчитывает:

> **Расчетную типовую стоимость путешествия** — воспроизводимую оценку стоимости заданного сценария на основе доступных рыночных предложений, выбранного профиля расчета и активной версии методики.

## 3. Входит в MVP

### 3.1. Источники и сбор

- проверка доступности и пригодности источников;
- реализация изолированных коннекторов;
- поддержка REST, MCP и HTTP-интеграций;
- Playwright или аналогичный браузерный парсинг только при необходимости;
- сохранение исходных ответов;
- ретраи, таймауты, backoff;
- технические метрики по каждому источнику.

### 3.2. Категории данных

- авиабилеты;
- железнодорожные билеты;
- проживание.

### 3.3. Режимы работы

- `MONITORING` — автоматический ежедневный расчет предустановленных сценариев;
- `ON_DEMAND` — расчет пользовательского сценария по запросу;
- `TEMPLATE` — предустановленные шаблоны для заполнения формы.

### 3.4. Сценарии путешествия

Пользователь работает с управляемым конструктором и выбирает только поддерживаемые параметры:

- город отправления;
- город назначения;
- дата начала поездки;
- дата окончания поездки;
- состав туристов;
- транспорт: авиа или ЖД;
- авиатариф;
- класс ЖД;
- тип размещения;
- звездность;
- питание;
- условие отмены для проживания;
- профиль расчета.

Каждая уникальная комбинация параметров является отдельным `TravelScenario`.

### 3.5. Расчетный движок

- валидация сценария;
- построение запросов к источникам;
- сбор raw-данных;
- нормализация;
- фильтрация по профилю;
- техническая и межисточниковая дедупликация;
- маркировка и исключение выбросов из агрегированного расчета;
- расчет P25, медианы, P75;
- межисточниковая агрегация;
- расчет стоимости транспорта;
- расчет стоимости проживания;
- расчет итоговой типовой стоимости;
- расчет стоимости на человека;
- определение полноты;
- расчет `Quality Score`;
- формирование объяснения результата;
- сохранение `ScenarioRun`.

### 3.6. Интерфейс

- главный управленческий дашборд;
- конструктор сценария;
- экран анализа направления;
- экран качества источников;
- минимальный административный экран;
- экспорт CSV/Excel.

### 3.7. Хранение

- raw-ответы;
- нормализованные предложения `Offer`;
- сценарии `TravelScenario`;
- профили `CalculationProfile`;
- результаты `ScenarioRun`;
- метрики качества;
- логи и ошибки;
- кэш результатов.

## 4. Не входит в MVP

- аналитика фактических туристических потоков;
- банковские транзакционные данные;
- мобильные данные;
- прогнозирование;
- машинное обучение;
- рекомендации;
- динамическое ценообразование;
- бронирование и покупка;
- платежи;
- комбинированный маршрут «туда самолетом, обратно поездом»;
- оптимизация расписания транспорта и заселения;
- анализ стыковок;
- развлечения;
- аренда автомобилей;
- трансферы;
- питание вне объекта размещения;
- сложный причинно-следственный анализ;
- Kubernetes;
- Kafka;
- Spark;
- микросервисная архитектура;
- внешний высоконагруженный API;
- полноценная система IAM, если корпоративный SSO недоступен.

# C — Context

## 1. Бизнес-контекст

Руководству необходим инструмент, позволяющий отвечать на вопросы:

- сколько сегодня стоит типовое путешествие по выбранному направлению;
- как изменилась стоимость за неделю и месяц;
- какие направления дорожают или дешевеют;
- из чего складывается стоимость;
- как стоимость зависит от даты поездки и горизонта бронирования;
- насколько надежны источники, на которых основан расчет.

Прототип должен быть аналитическим продуктом, а не набором парсеров.

## 2. География MVP

Поддерживаемые города:

- Москва;
- Санкт-Петербург;
- Краснодар;
- Сочи;
- Калининград;
- Южно-Сахалинск.

Город может использоваться как точка отправления и назначения.

Полный декартов набор маршрутов не создается автоматически. Для мониторинга используется управляемый CSV/YAML-каталог приоритетных сценариев.

## 3. Пользователи и роли

### VIEWER

- просмотр дашборда;
- просмотр предустановленных сценариев;
- экспорт;
- просмотр качества и актуальности расчета.

### ANALYST

- возможности VIEWER;
- расчет сценариев по запросу;
- детальный анализ;
- сравнение источников;
- просмотр объяснения расчета.

### ADMIN

- управление активностью сценариев;
- загрузка сценариев из YAML/CSV;
- управление профилями;
- активация и архивирование профилей;
- управление источниками;
- повторный запуск;
- просмотр технических ошибок.

## 4. Базовые пользовательские профили

### Базовый сценарий

- 2 взрослых;
- 1 номер;
- вместимость номера подтверждена минимум для 2 взрослых.

### Семейный шаблон

- 2 взрослых;
- 1 ребенок 7 лет;
- 1 номер, допускающий размещение состава.

Модель данных должна поддерживать массив возрастов детей, даже если интерфейс MVP использует один семейный шаблон.

## 5. Транспорт

### Авиа

Поддерживаемые тарифные режимы:

- `CHEAPEST`;
- `CABIN_BAGGAGE`;
- `CHECKED_BAGGAGE`.

Если источник не позволяет надежно определить багаж:

- предложение разрешено только для `CHEAPEST`;
- предложение не включается в `CABIN_BAGGAGE` и `CHECKED_BAGGAGE`;
- сохраняется статус неполной тарифной классификации.

Пересадки допускаются. Сохраняется:

- число пересадок;
- продолжительность;
- сегменты;
- перевозчик;
- номер рейса;
- времена отправления и прибытия.

Возвратность сохраняется, но не является обязательным фильтром MVP.

### ЖД

Поддерживаются отдельно:

- `RESERVED_SEAT`;
- `COMPARTMENT`.

Авиа и ЖД являются альтернативными вариантами сценария и не комбинируются.

## 6. Проживание

Тип размещения выбирается отдельно:

- `HOTEL`;
- `APARTMENT`;
- `GUEST_HOUSE`;
- `HOSTEL`;
- `SANATORIUM`, если источник подтвержден;
- `OTHER` — только для хранения и диагностики.

Звездность:

- 1–5 для гостиниц;
- `null` / `NOT_APPLICABLE` для типов, где звезды неприменимы;
- «без звезд» для гостиниц без официальной классификации.

Питание в пользовательском интерфейсе:

- `ANY`;
- `NO_MEALS`;
- `BREAKFAST`.

Дополнительные значения могут храниться в raw и normalized данных, но не обязаны выводиться в конструктор MVP.

Условия отмены:

- `ANY`;
- `FREE_CANCELLATION`, если источник надежно поддерживает классификацию.

Предложение без подтвержденной вместимости для заданного состава туристов не включается в расчет.

## 7. Даты и горизонт

Пользователь выбирает любые даты внутри доступного горизонта.

Для каждого источника хранится:

- минимальная поддерживаемая дата;
- максимальная поддерживаемая дата;
- технический booking horizon;
- дата последней проверки.

Общий пользовательский горизонт определяется не строгим пересечением всех источников, а наличием минимально достаточного покрытия:

- минимум один пригодный источник транспорта;
- минимум один пригодный источник проживания.

Система вычисляет `lead_time_days` как разницу между датой расчета и датой начала поездки.

## 8. Источники

Перечень API из исходного MD рассматривается как список кандидатов, а не подтвержденных интеграций.

В первые 5 рабочих дней выполняется `Source Qualification Spike` с решением `go/no-go`.

Для каждого источника проверяются:

- реальная доступность;
- авторизация;
- юридическая допустимость;
- покрытие городов;
- произвольные даты;
- число пассажиров;
- round-trip;
- багаж;
- пересадки;
- классы ЖД;
- тип размещения;
- звездность;
- питание;
- отмена;
- квоты;
- latency;
- стабильность;
- право хранения;
- ограничения автоматического доступа.

## 9. Технологический контекст

Рекомендуемый стек MVP:

- Python 3.12+;
- FastAPI;
- PostgreSQL;
- SQLAlchemy / Alembic;
- Pydantic;
- httpx;
- MCP client;
- APScheduler или cron;
- Streamlit;
- S3-compatible storage / MinIO или файловое raw-хранилище;
- Redis для кэша, если доступен;
- Docker Compose;
- pytest;
- pandas / openpyxl для экспорта;
- структурированное логирование;
- Prometheus-compatible метрики опционально.

Инфраструктура:

- 1 Ubuntu VM;
- 4–8 vCPU;
- 16–32 ГБ RAM;
- SSD 200–500 ГБ;
- открытый интернет или корпоративный proxy;
- внутренний веб-доступ;
- ежедневный backup PostgreSQL и raw storage.

Если Redis недоступен, допустим PostgreSQL-backed cache. In-memory cache нельзя использовать как единственное решение при нескольких процессах.

## 10. Авторизация

Предпочтительно использовать существующий Keycloak/SSO.

Если корпоративный IAM недоступен, допускается упрощенная локальная авторизация для MVP.

Закрытый доступ без авторизации допустим только как временный deployment mode и должен быть явно отражен в ограничениях.

# O — Objective

## 1. Конечная цель

Подтвердить, что организация способна:

- регулярно получать рыночные предложения;
- приводить данные разных источников к общей модели;
- воспроизводимо рассчитывать типовую стоимость путешествия;
- накапливать исторические снимки рынка;
- выявлять изменения стоимости;
- оценивать качество и устойчивость источников;
- обосновать переход к промышленному этапу.

## 2. Product KPI

### Покрытие

- 6 городов;
- не менее 100 Monitoring Scenario;
- минимум 2 пригодных транспортных источника;
- минимум 2 пригодных источника проживания.

Ограничение: «2 источника транспорта» трактуется как два пригодных источника в транспортном контуре, а не обязательно два источника для каждого вида транспорта.

### Стабильность

Не менее 80% ежедневных сценарных задач завершаются:

- `SUCCESS`;
- либо `PARTIAL_SUCCESS` с `Quality Score` выше установленного порога.

Это допущение MVP. Доля `SUCCESS` и `PARTIAL_SUCCESS` должна показываться отдельно.

### Производительность

- cached result: до 2 секунд;
- новый On-demand расчет: до 30 секунд в 90% случаев;
- после 30 секунд показывается промежуточный статус или частичный результат;
- дашборд: до 3 секунд для типового фильтрованного запроса по агрегатам.

### История

Каждый `ScenarioRun` сохраняет:

- дату расчета;
- параметры сценария;
- версию профиля;
- версии нормализации и движка;
- источники;
- количество предложений;
- P25;
- median;
- P75;
- компонентные стоимости;
- итог;
- статус;
- Quality Score.

### Качество

Для каждого источника и сценария рассчитываются:

- успешность;
- полнота;
- число предложений;
- доля невалидных записей;
- доля неклассифицированных тарифов;
- свежесть;
- межисточниковое расхождение;
- ошибки;
- latency.

### Пользовательский результат

Пользователь должен:

- открыть главный дашборд;
- выбрать поддерживаемый сценарий;
- выполнить On-demand расчет;
- увидеть детализацию;
- увидеть диапазон;
- понять источник результата;
- экспортировать данные.

## 3. Definition of Done

MVP считается завершенным, если:

1. пройден Source Qualification Spike;
2. подключены минимум 2 пригодных транспортных источника;
3. подключены минимум 2 пригодных источника проживания;
4. ежедневно рассчитываются минимум 100 сценариев;
5. работает управляемый On-demand конструктор;
6. raw-ответы сохраняются;
7. предложения нормализуются;
8. ScenarioRun сохраняется бессрочно;
9. Calculation Profile версионируется;
10. работает медианная агрегация;
11. рассчитываются P25–P75;
12. рассчитывается Quality Score;
13. поддерживаются частичные результаты;
14. работает Result Cache;
15. реализован главный дашборд;
16. реализован экран качества;
17. реализован экспорт CSV/Excel;
18. реализованы роли;
19. выполнен challenge set из 20–30 сценариев;
20. подготовлены README, runbook, schema description и инструкции администратора.

# P — Process

## 1. Основной pipeline

```text
TravelScenario
    +
CalculationProfile
    +
Calculation Date
        ↓
Validate Scenario
        ↓
Resolve Supported Horizon
        ↓
Build Provider Requests
        ↓
Read Result Cache
        ↓
Collect Raw Offers
        ↓
Persist Raw Responses
        ↓
Normalize Offers
        ↓
Validate and Classify
        ↓
Filter by Calculation Profile
        ↓
Technical Deduplication
        ↓
Cross-source Equivalence Linking
        ↓
Outlier Marking
        ↓
Source Eligibility Check
        ↓
Per-source Aggregation
        ↓
Cross-source Aggregation
        ↓
Combine Components
        ↓
Calculate Quality Score
        ↓
Create Explainability Payload
        ↓
Persist ScenarioRun
        ↓
Update Cache
        ↓
Return Result
```

- `error_summary`.

## 3. Валидация сценария

Проверяется:

- поддержка городов;
- origin != destination;
- даты;
- return_date > departure_date;
- доступный горизонт;
- поддержка транспорта;
- совместимость тарифа;
- класс ЖД;
- тип размещения;
- допустимость звездности;
- состав туристов;
- вместимость;
- питание;
- активность профиля.

Невалидный сценарий завершается до внешних запросов.

## 6. Дедупликация

### Technical duplicate

Удаляется из расчетной выборки.

### Cross-source equivalent offer

Не удаляется, а связывается общей группой, чтобы сохранять межисточниковое сравнение.

## 7. Выбросы

По умолчанию используется IQR:

- lower bound = Q1 − 1.5 × IQR;
- upper bound = Q3 + 1.5 × IQR.

Выбросы:

- сохраняются в raw и normalized слоях;
- маркируются;
- исключаются из основной агрегированной оценки;
- отображаются в диагностике.

Правило конфигурируемо в Calculation Profile.

## 8. Допуск источника

Источник участвует в итоговом расчете компонента, если:

- запрос завершился технически успешно;
- данные не старше установленного порога;
- получено минимальное число валидных предложений;
- после дедупликации осталось достаточно записей;
- доля невалидных записей ниже порога;
- предложения соответствуют профилю;
- обязательные поля определены.

Стартовые настройки:

- `min_valid_offers = 5`;
- `max_data_age_minutes = 60`;
- `max_invalid_offer_ratio = 0.30`;
- `max_unclassified_fare_ratio = 0.40`.

Значения конфигурируемы и калибруются на challenge set.

## 9. Агрегация

### Внутри источника

Рассчитываются:

- min;
- P25;
- median;
- P75;
- max;
- count.

Основной показатель — median.

### Между источниками

- сначала рассчитывается медиана каждого пригодного источника;
- затем рассчитывается медиана между источниками.

При 2 источниках:

- итог — среднее двух source median;
- обе source median показываются;
- рассчитывается межисточниковое расхождение;
- Quality Score снижается при высоком расхождении.

При 1 источнике:

- его медиана используется;
- статус `COMPLETE_SINGLE_SOURCE`;
- Quality Score снижается;
- показывается предупреждение.

При 0 источников:

- компонент отсутствует;
- итоговая полная стоимость не рассчитывается.

## 10. Формула стоимости

```text
transport_total_price =
стоимость всех пассажиров туда и обратно
```

```text
hotel_total_price =
стоимость одного подходящего номера за весь период
```

```text
total_estimated_cost =
transport_component_median + hotel_component_median
```

```text
price_per_person =
total_estimated_cost / traveler_count
```

Официальное название показателя:

> Расчетная типовая стоимость путешествия.

Сумма компонентных медиан не трактуется как медиана всех возможных комбинаций.

## 11. Статусы

- `UNSUPPORTED`;

Компонентные:

- `PARTIAL_TRANSPORT_MISSING`;
- `PARTIAL_HOTEL_MISSING`;

При отсутствии компонента:

- имеющаяся стоимость показывается;

- итоговая полная стоимость не рассчитывается;
- старое значение автоматически не подставляется.

## 12. Quality Score

Стартовая модель:

- полнота компонентов — 30%;
- число источников — 20%;
- число предложений — 15%;
- согласованность источников — 15%;
- свежесть — 10%;
- стабильность коннекторов — 10%.

Порог `PARTIAL_SUCCESS`:

- стартово `Quality Score >= 60`;
- конфигурируемо;
- подлежит проверке на challenge set.

Отдельно выводятся:

- доля SUCCESS;
- доля PARTIAL_SUCCESS;
- доля полных расчетов;
- средний Quality Score.

## 2. Challenge set

- разные даты;

- разные тарифы;

- сравнить с агрегатами;
- объяснить расхождение;
- исправить mapping или policy;

## 3. Функциональные acceptance criteria

### Сценарий

- невалидный сценарий не вызывает внешние API;
- уникальная комбинация имеет стабильный fingerprint;
- одинаковый запрос попадает в кэш.

### Коннектор

- изолирован от движка;
- сохраняет raw;
- возвращает единый контракт;
- имеет timeout;
- имеет retry;
- ошибки не обрушивают весь расчет.

### Нормализация

- цена и валюта корректны;
- round-trip не дублируется;
- цена отеля — за весь период;
- вместимость подтверждена;
- багаж классифицирован;
- неизвестный багаж не попадает в baggage profiles.

### Агрегация

- медиана рассчитывается корректно;
- P25–P75 корректны;
- source eligibility соблюдается;
- один источник снижает качество;
- отсутствующий компонент не подменяется старым.

### История

- ScenarioRun immutable;
- версия профиля сохранена;
- старый run не меняется после новой версии профиля.

### Экспорт

- экспорт соответствует выбранному фильтру;
- числа и даты корректны;
- поля качества присутствуют.

## 4. Нефункциональные критерии

- cached result <= 2 секунд;
- 90-й перцентиль нового расчета <= 30 секунд;
- ежедневный batch поддерживает 100 сценариев;
- повторный запуск идемпотентен;
- падение одного источника не обрушивает остальные;
- backup восстанавливается;
- секреты не хранятся в репозитории;
- логи не содержат токены;
- raw storage имеет retention;
- UI показывает время актуальности.

## 5. Failure cases

Обязательные тесты:

- API timeout;
- rate limit;
- 401/403;
- schema drift;
- пустой ответ;
- дубликаты;
- цена = 0;
- валюта не RUB;
- отсутствует багаж;
- отсутствует вместимость;
- только один источник;
- расхождение > 30%;
- нет отеля;
- нет транспорта;
- истекшая дата;
- неподдерживаемый маршрут;
- кэш недоступен;
- PostgreSQL недоступен;
- raw storage недоступен;
- partial batch.

## 6. Риски ложной интерпретации

UI и документация должны явно сообщать:

- система оценивает типовую стоимость;
- цена не является офертой;
- результат не является средним чеком;
- стоимость не учитывает развлечения и локальные расходы;
- расписание транспорта и заселение не оптимизируются;
- расчет зависит от доступности источников;
- история до накопления достаточного числа точек ограничена.

## 7. Security

- секреты через env/secrets;
- RBAC;
- CSRF/session protection;
- rate limiting;
- audit административных действий;
- запрет произвольных URL в коннекторах;
- allowlist источников;
- валидация входа;
- защита от CSV injection в экспорте;
- dependency scan;
- минимальные права БД;
- backup encryption, если требуется политикой.
