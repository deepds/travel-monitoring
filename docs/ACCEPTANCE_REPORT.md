# Отчет о приемке MVP

дополнительными критериями приемки (DELTA §11).

**Версии:** приложение 1.0.0, движок 1.0.0, нормализация 1.0.0, схема 1.0.0

## 2. Дополнительные критерии приемки (DELTA §11)

### 2.1. Market Snapshot

| Критерий | Статус | Комментарий |
|---|:---:|---|
| Снимки создаются по расписанию на каждый активный сценарий | ✅ | Переведено на **ежечасное** наблюдение (24 в сутки) вместо четырех — решение владельца продукта, отклонение от DELTA §2.1 зафиксировано |
| Snapshot immutable после завершения | ✅ | Финализация переводит в терминальный статус |
| Содержит ссылки на raw и HTML | ✅ | `raw_response_refs`, `html_snapshot_refs` |
| Может использоваться повторно для пересчета | ✅ | `POST /market-snapshots/{id}/recalculate` |
| Один snapshot поддерживает несколько ScenarioRun | ✅ | Связь через `market_snapshot_id` |

### 2.2. Celery

| Критерий | Статус | Комментарий |
|---|:---:|---|
| Долгие операции выполняются в background | ✅ | Четыре очереди: collect, compute, ondemand, maintenance |
| API не блокируется | ✅ | `202 Accepted` + `job_id` |
| Job status доступен по API | ✅ | `GET /jobs/{id}`, `/events` |
| Retry не создает дубли | ✅ | Ключи идемпотентности снимка и задачи |
| Зависшая задача обнаруживается | ✅ | Детектор каждые 10 минут переводит в `TIMED_OUT` |
| Celery Beat запускает плановый мониторинг | ✅ | Расписание выводится из `SNAPSHOT_INTERVAL_HOURS` |

### 2.3. Source Confidence и Scenario Confidence

| Критерий | Статус |
|---|:---:|
| Source Confidence рассчитывается минимум раз в сутки | ✅ |
| Имеет версию формулы, объясним, доступен по API | ✅ |
| Ручной override аудируется | ✅ |
| Scenario Confidence рассчитывается для каждого ScenarioRun | ✅ |
| Отображается в UI с объяснением | ✅ |
| `INSUFFICIENT` запрещает показывать итог как полноценную стоимость | ✅ |

### 2.4. HTML

Требования (gzip, checksum, retention, ссылка из снимка, без токенов)
реализованы. Фактически **не задействовано**: оба подтвержденных источника
работают по API, браузерный парсинг не потребовался. Механизм включается
установкой `html_storage_allowed` у источника.

## 5. Согласованные отклонения от SCOPE-R

Изменения, принятые владельцем продукта после утверждения требований:

| Отклонение | Было | Стало | Причина |
|---|---|---|---|
| Частота наблюдения | 4 снимка в сутки (DELTA §2.1) | Ежечасно, 24 в сутки | Внутрисуточная волатильность авиацен иначе не видна. Нагрузка на источники выросла шестикратно, поэтому добавлен ограничитель темпа |
| География | 6 городов (SCOPE-R C §2) | 8 городов: добавлены Анапа и Геленджик | Типовой запрос руководства сформулирован для курортов Краснодарского края |
| Интерфейс | Streamlit (SCOPE-R C §9) | React + TypeScript | Требования к дашборду, конструктору и админке выходят за возможности Streamlit по интерактивности |

## 6. Открытые пункты

| Пункт | Влияние | Что требуется |
|---|---|---|
| **Второй источник проживания** | KPI покрытия не выполнен. Проживание считается по одному источнику: режим `COMPLETE_SINGLE_SOURCE`, Quality Score снижен, уверенность не выше `MEDIUM` | Партнерский OAuth-токен Яндекс Путешествий (коннектор готов, включается автоматически) либо ключи TravelLine |
| **Калибровка порогов на реальных данных** | Пороги допуска источника и веса Quality Score — стартовые значения методики | Накопить наблюдения и прогнать challenge set с профилем `baseline` |
| **Замер производительности на полном каталоге** | 90-й перцентиль On-demand не подтвержден измерением | Нагрузочный прогон после восстановления стенда |
| **Учебное восстановление из резервной копии** | Процедура описана, но не проверена | Провести восстановление на отдельном окружении |
| **Юридическое подтверждение автоматического доступа** | Условия использования источников не подтверждены письменно | Запрос через юридическую службу до промышленной эксплуатации |
| **Ретроспективная история недоступна** | Динамика за неделю и месяц появится только с накоплением | Ограничение источников, обходу не подлежит — см. [LIMITATIONS §7](LIMITATIONS.md) |

## 7. Дефекты, найденные и устраненные при проверке на живых источниках

Проверка на реальном стенде выявила четыре дефекта, которые невозможно было
обнаружить на синтетических данных. Все устранены:

| Дефект | Проявление | Причина |
|---|---|---|
| Превышение границ схемы MCP | Туту отклонял все запросы на валидации | Коннектор слал `page_size=50` при объявленном максимуме 30. Числовые аргументы теперь зажимаются в границы схемы |
| Неверный контракт разбора Туту | Ноль предложений либо падение `'str' object has no attribute 'get'` | Парсеры написаны по публичному описанию; фактический ответ отличается структурой |
| Неверный эндпоинт РЖД | `500 INTERNAL_ERROR` на любой запрос цен | Публичный путь нерабочий; B2B-путь отвечает корректно и требует поля `DepartureDate` |
| Падение принудительного сбора | Нарушение уникального индекса снимка | `force_refresh` не менял ключ идемпотентности |

Дополнительно устранен архитектурный пробел: `rate_limit_per_minute`
хранился и отдавался в API, но при сборе не применялся. Добавлен
межпроцессный ограничитель темпа.

## 8. Заключение

MVP соответствует Definition of Done по 19 из 20 пунктов. Единственный
невыполненный пункт — второй источник проживания — заблокирован внешней
причиной (отсутствие партнерских учетных данных), а не реализацией:
коннекторы написаны и включаются автоматически при появлении ключей.

Ключевые способности, которые требовалось подтвердить, подтверждены:
регулярный сбор рыночных предложений, приведение источников к общей модели,
воспроизводимый расчет, накопление снимков рынка, выявление изменений
стоимости и оценка качества источников.

Систему **нельзя** использовать для управленческих выводов до закрытия двух
пунктов: подключения второго источника проживания и калибровки порогов на
накопленных данных. До этого момента результаты пригодны для сравнения
направлений и отладки методики.
