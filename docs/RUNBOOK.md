# Runbook

Эксплуатационное руководство: развертывание, регламентные операции,
диагностика, резервное копирование и восстановление.

Адресат — дежурный инженер и администратор платформы.

---

## 1. Состав стека

| Сервис | Роль | Порт | Критичность |
|---|---|---:|---|
| `postgres` | Основное хранилище: сценарии, снимки, предложения, результаты | 5432 | Критичен |
| `redis` | Брокер Celery, result backend, быстрый слой Result Cache | 6379 | Деградация |
| `api` | FastAPI `/api/v1` | 8000 | Критичен |
| `worker` | Celery-воркер: сбор, расчет, обслуживание | — | Критичен |
| `beat` | Celery Beat: расписание снимков и регламентов | — | Критичен |
| `ui` | React-интерфейс за nginx | 8080 | Деградация |
| `migrate` | Разовое применение миграций (профиль `tools`) | — | — |
| `bootstrap` | Разовая инициализация справочников (профиль `tools`) | — | — |

Очереди Celery разделены намеренно: `collect` (сеть), `compute` (расчет),
`ondemand` (пользовательские запросы), `maintenance` (регламенты). Обслуживание
не должно вытеснять пользовательские расчеты.

## 2. Первичное развертывание

```bash
git clone <repo> && cd travel_monitoring
cp .env.example .env
```

Заполните обязательные секреты — без них стек не поднимется в проде:

```bash
echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)" >> .env
echo "JWT_SECRET=$(openssl rand -hex 32)" >> .env
echo "BOOTSTRAP_ADMIN_PASSWORD=$(openssl rand -hex 12)" >> .env
```

Примените миграции и инициализируйте справочники:

```bash
docker compose --profile tools run --rm bootstrap
```

Команда дожидается готовности PostgreSQL, применяет Alembic-миграции и
заполняет города, профили расчета, источники, шаблоны и учетные записи.
Если пароли пользователей не заданы в окружении, они генерируются и
однократно печатаются в вывод — сохраните их сразу, в БД лежит только хеш.

Поднимите сервисы:

```bash
docker compose up -d
docker compose ps
```

Загрузите каталог сценариев мониторинга:

```bash
docker compose exec api python -m tco.cli import-scenarios catalog/monitoring_scenarios.csv
```

Проверьте готовность:

```bash
curl -fsS http://localhost:8000/api/v1/health/ready
curl -fsS http://localhost:8000/api/v1/version
```

## 3. Регламентные операции

### 3.1. Расписание Celery Beat

Суточный цикл разнесен по компонентам и по времени с запасом: одновременный
залп из 1695 сценариев источник не выдерживает — именно он открыл размыкатель
цепи 6 августа. К десяти утра все закончено, дальше четырнадцать часов запаса
на повтор.

| Время | Задача | Что собирает | Окно |
|---|---|---|---|
| 00:30 | `maintain_observation_grid` | достройка сетки на новый день горизонта | 10 мин |
| 01:00 | `refresh_all_monitoring_scenarios` | ЖД, 600 сценариев | 2 ч |
| 03:30 | `refresh_all_monitoring_scenarios` | авиа, 600 сценариев | 2 ч |
| 06:00 | `refresh_all_monitoring_scenarios` | проживание на ночь, 450 | 1,5 ч |
| 08:00 | `refresh_all_monitoring_scenarios` | контрольные пятидневные, 45 | 15 мин |
| 09:00 | `backfill_missing_observations` | досбор дыр | 1 ч |
| 10:00 | `daily_collection_report` | сводка качества за сутки | — |

Окна отбираются тегами сетки (`showcase-rail`, `showcase-avia`,
`showcase-stay-1n`, `showcase-stay-5n`): сценарий попадает ровно в одно, иначе
он либо соберется дважды, либо не соберется вовсе.

Остальное обслуживание:

| Задача | Расписание | Назначение |
|---|---|---|
| `refresh_all_monitoring_scenarios` | ежечасно, :05 | Каталог без тега `cadence:daily` |
| `watch_collection_progress` | каждые 5 минут | Сторож застрявшего сбора |
| `health_check_all_sources` | ежечасно, :20 | Доступность источников |
| `calculate_source_confidence_all` | ежедневно, 02:40 | Пересчет доверия источникам |
| `refresh_source_horizons` | ежедневно, 03:50 | Обновление технического горизонта |
| `cleanup_expired_data` | ежедневно, 04:15 | Retention: raw, HTML, offers, экспорты |
| `cleanup_expired_cache` | ежечасно, :35 | Очистка истекшего кэша |
| `detect_stalled_jobs` | каждые 10 минут | Обнаружение зависших задач |

### 3.1.1. Два воркера и кто кого чинит

Воркеров два, и это не про производительность. Пока один процесс держал
`collect`, `compute`, `ondemand` и `maintenance` разом, забитый сбором пул не
выполнял и собственного лечения — система теряла способность чинить себя
ровно тогда, когда это нужно.

| Контейнер | Очереди | Роль |
|---|---|---|
| `worker` | `collect`, `compute` | Сбор и расчет: все длинное и сетевое |
| `worker-service` | `maintenance`, `ondemand` | Обслуживание и запросы пользователя |

Три линии лечения, каждая следующая включается, когда предыдущая не помогла:

1. **Сторож** (`watch_collection_progress`, каждые 5 минут в
   `worker-service`) — обнаружив, что очередь сбора не разбирается, просит
   воркеров перезапустить пул.
2. **Проверка живости** — `python -m tco.tasks.health` смотрит на движение
   очереди, а не на ответ процесса: `celery inspect ping` отвечает из главного
   процесса и отвечает исправно, когда весь пул занят намертво. Контейнер, где
   задачи ждут, а за четверть часа ни одна не завершилась, объявляется больным.
3. **`autoheal`** — перезапускает контейнер, объявивший себя больным.
   `restart: unless-stopped` этого не сделает: зависший контейнер не падает.

Посмотреть, что видит проверка:

```bash
docker compose exec worker python -m tco.tasks.health; echo "код возврата: $?"
```

Проверить, что Beat жив:

```bash
docker compose logs --tail=50 beat
docker compose exec api python -m tco.cli health
```

```bash
docker compose exec api python -m tco.cli retention
```

Политика по умолчанию: raw и HTML — 45 дней, нормализованные предложения —

переменными `RETENTION_*`.

### 3.5. Каталог вне пяти городов витрины

Платформа решала три задачи сразу; заказчик оставил витрину. Каталог из 163
сценариев по восьми городам продолжал собираться ежечасно и занимал около трех
тысяч обращений в сутки — ровно тот запас, который нужен пагинации и
однодневным броням.

Операция мягкая: сценарии деактивируются, накопленные снимки, расчеты и
предложения остаются на месте, экраны каталога доступны под ролью ADMIN.

```bash
docker compose exec api python scripts/retire_catalog.py --dry-run
```

```bash
docker compose exec api python scripts/retire_catalog.py --yes
```

Возврат — один запуск: `scripts/retire_catalog.py --restore --yes`. Поднимутся
только сценарии, снятые этой операцией: она помечает их в примечании, и
выключенные по другим причинам (закрытый аэропорт Анапы, стыковки Краснодар —
Сочи) остаются выключенными.

### 3.6. Удаление наблюдений, которые непригодны в принципе

Операция необратима и по умолчанию запрещена методикой: наблюдения
невосполнимы, источники не отдают историю цен. Она нужна там, где данные не
просто неверны, а несопоставимы с новыми — например, собраны с обрезанной
выдачей или на другой длительности брони, и никакой пересчет их не исправит.

```bash
docker compose exec api python scripts/purge_observations.py --before 2026-08-08 --dry-run
```

```bash
docker compose exec -d api python scripts/purge_observations.py --before 2026-08-08 --yes
```

Обратите внимание на `-d`: обрыв SSH посреди долгой операции оставляет живую
транзакцию, которая держит блокировки и не завершается никогда — клиента,
который ее закроет, больше нет. За ней выстраивается очередь, и встает все,
включая плановый сбор.

**Остановить контейнер — не значит остановить запрос.** `docker stop` убивает
клиента, а серверный процесс PostgreSQL продолжает выполнять начатое: 7 августа
снятый таким образом `DELETE` прожил еще двадцать минут и заблокировал
построение индекса, которое ждало завершения чужих транзакций. Смотреть надо в
саму СУБД:

```bash
docker exec -i tco-postgres-1 psql -U tco -d tco -c "SELECT pid, state, now()-query_start AS dur, left(query,60) FROM pg_stat_activity WHERE datname='tco' AND state <> 'idle' ORDER BY query_start;"
```

Снять зависший запрос:

```bash
docker exec -i tco-postgres-1 psql -U tco -d tco -c "SELECT pg_terminate_backend(PID_ИЗ_ЗАПРОСА_ВЫШЕ);"
```

Переживают удаление: записи аудита, журнал задач (обнуляется только ссылка) и
метрики источников — последние сносятся только ключом `--with-source-metrics`,
когда накоплены за время неверной работы сбора.

## 4. Диагностика

### 4.1. Быстрая проверка состояния

```bash
docker compose ps
curl -s http://localhost:8000/api/v1/health | python -m json.tool
docker compose exec api python -m tco.cli health
```

`/health/ready` проверяет БД, брокер и raw storage; `/health/live` отвечает,
пока процесс жив. Оркестратор должен использовать `ready` для трафика и
`live` для перезапуска.

### 4.2. Типовые инциденты

#### Расчеты идут, но все сценарии в статусе `NO_DATA`

Вероятная причина — источники выключены или не прошли квалификацию.

```bash
curl -s http://localhost:8000/api/v1/sources -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

Проверьте `is_enabled`, `qualification_status` и `circuit_open_until`.
Разомкнутый предохранитель закрывается автоматически по истечении
`CONNECTOR_CIRCUIT_BREAKER_COOLDOWN_SECONDS`, принудительно — через
`POST /api/v1/sources/{id}/enable`.

#### Источник помечен как недоступный

```bash
curl -X POST http://localhost:8000/api/v1/sources/{id}/health-check \
  -H "Authorization: Bearer $TOKEN"
```

Разберите `last_error` и `error_breakdown` на экране качества источников.
`AUTH_ERROR` означает истекшие или отсутствующие учетные данные —
проверьте `YANDEX_TRAVEL_TOKEN` / `TRAVELLINE_CLIENT_*` в окружении.

#### Задачи копятся в очереди

```bash
docker compose exec redis redis-cli llen collect
docker compose exec redis redis-cli llen compute
docker compose logs --tail=100 worker
```

Масштабирование воркеров:

```bash
docker compose up -d --scale worker=3
```

#### Зависшие задачи

Детектор переводит задачи без heartbeat дольше 15 минут в `TIMED_OUT`
каждые 10 минут. Список:

```bash
curl -s "http://localhost:8000/api/v1/jobs?status=TIMED_OUT" \
  -H "Authorization: Bearer $TOKEN"
```

Повторный запуск: `POST /api/v1/jobs/{id}/retry`. Ретрай не создает
дубликат снимка — идемпотентность обеспечивается ключом задачи.

#### Redis недоступен

Result Cache деградирует на слой PostgreSQL и продолжает работать.
Celery без брокера ставить задачи не может: API вернет `503`
(`BROKER_UNAVAILABLE`), синхронные расчеты через CLI останутся доступны.

#### PostgreSQL недоступен

Полная остановка обслуживания. Проверьте том `pgdata` и логи:

```bash
docker compose logs --tail=100 postgres
docker volume inspect travel_monitoring_pgdata
```

#### Raw storage недоступен

Сбор продолжается: ошибка фиксируется в метриках источника и в
`error_summary` снимка, но расчет не срывается. Нормализованные предложения
сохраняются в БД, теряется только возможность аудита исходных ответов.

### 4.3. Диагностика конкретного расчета

```bash
curl -s http://localhost:8000/api/v1/scenario-runs/{run_id}/explain \
  -H "Authorization: Bearer $TOKEN" | python -m json.tool
```

Ответ содержит: использованные источники, число полученных и исключенных
предложений, медиану каждого источника, межисточниковое расхождение,
примененный профиль и версии, причины снижения Quality Score.

Разрез по источникам — `/scenario-runs/{run_id}/source-breakdown`.

### 4.4. Грабли первичного развертывания на отдельной ВМ

Собрано с развертывания в корпоративной сети: каждый пункт — реально
наступивший случай, а не гипотеза. Порядок совпадает с тем, в котором они
всплывают.

**`Cannot connect to the Docker daemon` сразу после установки.** Под `sudo`
это не про права: демон не запущен. На минимальных образах и в ВМ, где systemd
не PID 1, пакет не стартует сам.

```bash
sudo systemctl enable --now docker
```

**`invalid project name "tco\r"` и `$'\r': command not found` в deploy.sh.**
`.env` с виндовыми переводами строк. Compose свой парсер от CR чистит, поэтому
`up -d` проходит и создает иллюзию исправной конфигурации, а `deploy.sh` читает
файл через `. ./.env`, и CR остается в значениях. В репозитории это закрыто
через `.gitattributes`, но уже созданный `.env` нужно вылечить:

```bash
sed -i 's/\r$//' ~/tco/.env
```

**502 на `/api/` при живом API.** nginx интерфейса резолвит адрес `api` один
раз при старте, а контейнер `api` при пересоздании получает новый адрес.
Контейнер `ui` пересоздается только при изменении фронтенда, поэтому после
правки одного бэкенда интерфейс стучится по старому адресу. `deploy.sh`
перезапускает `ui` сам; если поднимали руками:

```bash
cd ~/tco && sudo docker compose restart ui
```

**`curl: URL rejected: Port number was not a decimal number` в конце
deploy.sh.** Всплывало при `API_PORT=127.0.0.1:8000`. Исправлено — из значения
берется только номер порта. На старых копиях скрипта проверяйте здоровье через
интерфейс: `curl -fsS http://127.0.0.1:8080/api/v1/health/ready`.

**UFW не закрывает опубликованный порт контейнера.** Docker пишет правила в
цепочку `DOCKER` таблицы `nat`, и они срабатывают раньше правил UFW —
`ufw deny 8000` создает ложное ощущение закрытого порта. Ограничивать нужно
через `DOCKER-USER`, причем по исходному порту назначения: к моменту
`DOCKER-USER` адрес уже переписан DNAT, и `--dport 8080` не совпадет ни с чем.

```bash
sudo iptables -I DOCKER-USER -p tcp -m conntrack --ctorigdstport 8080 ! -s 10.0.0.0/8 -j DROP
```

Подсеть в примере — пример. Свою смотрите в `ip -4 addr show scope global`:
ошибка здесь закрывает интерфейс от тех, кому он предназначен, и выглядит как
неработающий стенд. Установка `iptables-persistent` удаляет `ufw` — на чистой
ВМ он обычно и не включен, но проверьте.

**Пустые экраны на свежей установке.** Сценарии импортированы, наблюдений нет,
а плановый сбор копит историю неделями. Разворачивайте демонстрационный слепок:

```bash
cd ~/tco && bash scripts/seed-restore.sh
```

**Пароль администратора негде взять.** Если `BOOTSTRAP_*_PASSWORD` не заданы,
пароли генерируются и попадают только в stdout команды `bootstrap` — в логах
контейнеров их нет. Задавайте явно в `.env` до первого запуска, иначе:

```bash
sudo docker compose exec api python -m tco.cli reset-password admin
```

**Исходящий доступ.** Сборке нужны `download.docker.com`, `deb.debian.org`,
`registry-1.docker.io`, `pypi.org`, `files.pythonhosted.org`,
`registry.npmjs.org`; работе — `mcp.tutu.ru` и `ticket.rzd.ru`. Если наружу
только через прокси, его задают в трех местах: демону Docker, сборке и
контейнерам (`HTTP_PROXY`/`HTTPS_PROXY` в `.env` — `httpx` их подхватывает).
Проверять связность нужно **из контейнера**, а не с хоста: в корпоративной сети
хост видит источник, когда контейнер уже нет.

```bash
cd ~/tco && bash scripts/check-sources.sh
```

## 5. Сохранность накопленных данных

Это самый ценный актив платформы. Источники **не отдают историю цен**:
утраченный снимок рынка восстановить неоткуда — его можно только накопить
заново, потратив столько же календарного времени.

### 5.0. Как устроена защита

**База, сырые ответы и выгрузки лежат в bind-mount по абсолютному пути**
`DATA_ROOT` (по умолчанию `/srv/tco`) — вне каталога с исходниками. Это
закрывает два типовых способа потерять данные:

| Опасность | Почему возникает | Как закрыта |
|---|---|---|
| Развертывание из другого каталога | Имя named-тома выводится из имени каталога проекта: из `~/tco` получается `tco_pgdata`, из `~/travel_monitoring` — `travel_monitoring_pgdata`. Данные целы, но стек их не видит | Bind-mount по абсолютному пути + явный `COMPOSE_PROJECT_NAME` |
| Пересоздание исходников | `git clone`, распаковка архива, `rm -rf` каталога проекта | Данные лежат вне каталога с исходниками |
| `docker compose down -v` | Ключ `-v` удаляет тома | В `scripts/deploy.sh` этой команды нет; на рабочем стенде выполнять вручную запрещено |

> **Никогда не выполняйте `docker compose down -v` на стенде с данными.**
> Для обновления есть `scripts/deploy.sh`, для остановки — `docker compose stop`.

Redis намеренно оставлен обычным томом: это брокер и кэш, его содержимое
воспроизводимо.

### 5.1. Обновление без потери данных

```bash
scripts/deploy.sh --pull
```

Скрипт выполняет строго в этом порядке: резервная копия → обновление кода →
сборка образов → миграции → перезапуск. Тома не удаляются. Если копия не
создалась, обновление останавливается.

После обновления скрипт печатает счетчики сценариев, снимков, расчетов и
предложений — расхождение с ожидаемым видно сразу, а не через неделю.

### 5.2. Полная передеплой-проверка

Порядок, при котором стек можно снести целиком и поднять заново из GitHub,
не потеряв наблюдений:

```bash
scripts/backup.sh                      # 1. копия
docker compose down                    # 2. БЕЗ ключа -v
rm -rf ~/tco && git clone <repo> ~/tco # 3. чистые исходники
cd ~/tco && cp /secure/place/.env .    # 4. .env из хранилища секретов
scripts/deploy.sh --skip-backup        # 5. подъем на существующих данных
```

Данные не затрагиваются: они в `DATA_ROOT`. Шаг 1 нужен на случай, если на
шаге 5 обнаружится несовместимость.

### 5.3. Поднять окружение «от релевантного слепка»

```bash
scp prod:/srv/tco-backups/latest/* /srv/tco-backups/imported/
scripts/restore.sh /srv/tco-backups/imported
```

`restore.sh` проверяет контрольную сумму дампа, делает страховочную копию
текущего состояния, восстанавливает базу и сырые артефакты, доводит схему
миграциями до текущей версии и печатает счетчики. Так тестовый стенд
начинает не с нуля, а с накопленной аналитикой.

### 5.4. Что резервируется

| Данные | Способ | Периодичность | Критичность |
|---|---|---|---|
| PostgreSQL | `pg_dump` | Ежедневно | Критично: восстановлению не подлежит из других источников |
| Raw storage | Синхронизация каталога / S3 | Ежедневно | Важно: доказательная база аудита |
| `.env` | Хранилище секретов организации | При изменении | Критично |

`ScenarioRun` и метаданные снимков хранятся бессрочно и невосстановимы:
внешние источники не отдают исторические цены.

### 5.5. Снятие копии

```bash
scripts/backup.sh                       # в ${BACKUP_ROOT:-/srv/tco-backups}
scripts/backup.sh /mnt/nas/tco-backups  # в произвольный каталог
```

Копия содержит дамп базы в custom-формате, архив сырых артефактов и
манифест с версиями, контрольными суммами и счетчиками строк. Ссылка
`latest` всегда указывает на свежую копию.

Ежедневное расписание (cron на хосте):

```bash
0 5 * * * cd /home/cluster/tco && ./scripts/backup.sh >> /var/log/tco-backup.log 2>&1
```

### 5.6. Восстановление

```bash
scripts/restore.sh /srv/tco-backups/latest
```

Скрипт сверяет контрольную сумму, снимает страховочную копию текущего
состояния, останавливает потребителей (базу оставляет поднятой),
восстанавливает данные, применяет миграции и показывает счетчики.

> Восстановление обязано проверяться регулярно: невоспроизведенная
> резервная копия резервной копией не является. Учебное восстановление
> на отдельном окружении — не реже одного раза в квартал.

## 6. Обновление версии

```bash
git pull
docker compose build
docker compose --profile tools run --rm migrate
docker compose up -d
```

Миграции применяются до подъема новых контейнеров. При изменении
`ENGINE_VERSION` или `NORMALIZATION_VERSION` исторические `ScenarioRun`
**не пересчитываются**: они остаются с версиями, при которых были получены.
Сравнивать результаты разных версий следует через пересчет снимка
(`POST /api/v1/market-snapshots/{id}/recalculate`), а не подменой истории.

## 7. Мониторинг

Минимальный набор наблюдаемых метрик (SCOPE-R R §4):

| Метрика | Источник | Порог внимания |
|---|---|---|
| Connector success rate | `/api/v1/sources/{id}/metrics` | < 90% за сутки |
| Latency источника | там же | p95 > 20 с |
| Доля валидных предложений | там же | < 70% |
| Scenario success rate | `/api/v1/dashboard/quality` | < 80% |
| Доля частичных результатов | там же | рост неделя к неделе |
| Cache hit rate | `/api/v1/health` | резкое падение |
| Длительность batch | `/api/v1/admin/monitoring/jobs` | > 2 часов |
| Рост БД и raw storage | `df -h`, `pg_database_size` | > 80% диска |

KPI стабильности MVP: не менее 80% ежедневных сценарных задач завершаются
`SUCCESS` либо `PARTIAL_SUCCESS` с Quality Score выше порога. Доли `SUCCESS`
и `PARTIAL_SUCCESS` показываются раздельно.

## 8. Безопасность в эксплуатации

- Секреты только в окружении; `.env` не коммитится и не копируется в образ.
- Логи и аудит проходят вычистку: токены и пароли в них не попадают.
- Порт PostgreSQL по умолчанию слушает `127.0.0.1` — наружу не публикуется.
- Смена пароля: `python -m tco.cli reset-password <username>`.
- Режим `DEPLOYMENT_MODE=OPEN` отключает авторизацию. Допустим только как
  временный режим развертывания, отражается в `/api/v1/version` и в интерфейсе.
- Административные действия пишутся в аудит: `/api/v1/audit/events`.
