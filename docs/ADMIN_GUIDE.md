# Руководство администратора

Адресат — роль `ADMIN`. Документ описывает управление каталогом сценариев,
источниками, профилями расчета, задачами и доступом.

Все административные действия пишутся в аудит и доступны через
`GET /api/v1/audit/events`.

---

## 1. Роли и права

| Возможность | VIEWER | ANALYST | ADMIN |
|---|:---:|:---:|:---:|
| Дашборд, предустановленные сценарии, экспорт | + | + | + |
| Просмотр качества и актуальности расчета | + | + | + |
| Расчет по запросу, детальный анализ, сравнение источников | | + | + |
| Просмотр объяснения расчета | | + | + |
| Управление активностью сценариев, загрузка каталога | | | + |
| Управление профилями, активация и архивирование | | | + |
| Управление источниками, повторный запуск, технические ошибки | | | + |

Роли проверяются на backend: интерфейс скрывает недоступные действия, но
источником истины является API.

Смена пароля:

```bash
docker compose exec api python -m tco.cli reset-password analyst
```

## 2. Каталог сценариев мониторинга

### 2.1. Формат

Каталог загружается в CSV или YAML. Колонки CSV:

| Колонка | Обязательна | Значения |
|---|:---:|---|
| `code` | нет | Пусто — код будет построен из отпечатка |
| `name` | нет | Пусто — имя будет собрано автоматически |
| `origin_city_code` | **да** | `MOW`, `LED`, `KRR`, `AER`, `KGD`, `UUS` |
| `destination_city_code` | **да** | то же |
| `departure_date` | **да** | `YYYY-MM-DD` |
| `return_date` | **да** | `YYYY-MM-DD`, строго позже даты начала |
| `adults` | нет | 1–8, по умолчанию 2 |
| `children_ages` | нет | `7` или `4;11`, до 4 детей, возраст 0–17 |
| `transport_type` | нет | `AVIA` (по умолчанию) или `RAIL` |
| `flight_fare_type` | нет | `CHEAPEST`, `CABIN_BAGGAGE`, `CHECKED_BAGGAGE` |
| `rail_class` | нет | `COMPARTMENT`, `RESERVED_SEAT` |
| `accommodation_type` | нет | `HOTEL`, `APARTMENT`, `GUEST_HOUSE`, `HOSTEL`, `SANATORIUM` |
| `stars` | нет | `ANY`, `1`–`5`, `UNRATED`, `NOT_APPLICABLE` |
| `meal_type` | нет | `ANY`, `NO_MEALS`, `BREAKFAST` |
| `cancellation_filter` | нет | `ANY`, `FREE_CANCELLATION` |
| `active_from` / `active_until` | нет | Период активности; по умолчанию до даты возврата |
| `priority` | нет | Меньше — раньше в очереди мониторинга |
| `tags` | нет | Через `;` |
| `notes` | нет | Свободный текст |

Тариф значим только для своего вида транспорта: в авиасценарии `rail_class`
игнорируется, и наоборот.

### 2.2. Загрузка

Через API:

```bash
curl -X POST http://localhost:8000/api/v1/admin/scenarios/import \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@catalog/monitoring_scenarios.csv"
```

Импорт асинхронный: возвращается `job_id`. Статус и ошибки:

```bash
curl .../api/v1/admin/scenarios/import/{job_id}
curl .../api/v1/admin/scenarios/import/{job_id}/errors
```

Через CLI:

```bash
docker compose exec api python -m tco.cli import-scenarios catalog/monitoring_scenarios.csv
```

**Ошибочная строка не срывает импорт целиком**: она попадает в отчет с
номером строки и причиной, остальные строки загружаются.

### 2.3. Идентичность сценариев

Сценарий определяется отпечатком бизнес-параметров, а не кодом. Повторная
загрузка того же набора параметров не создаст дубликат — она вернет
существующий сценарий и при необходимости активирует его.

Следствие: контрольный сценарий из `challenge_set.csv` может совпасть с
сценарием мониторинга. Это штатно — одинаковые параметры есть один и тот же
объект наблюдения.

### 2.4. Регенерация каталога

Сценарии заданы абсолютными датами и автоматически деактивируются после
окончания поездки. Каталог перегенерируется:

```bash
python scripts/generate_catalog.py --base-date 2026-09-01
```

Скрипт формирует `catalog/monitoring_scenarios.csv` (не менее 100 сценариев)
и `catalog/challenge_set.csv` (20–30 контрольных) и проверяет эти границы.

### 2.5. Активация и удаление

```bash
POST   /api/v1/scenarios/{id}/activate
POST   /api/v1/scenarios/{id}/deactivate
DELETE /api/v1/scenarios/{id}        # мягкое удаление
```

Мягкое удаление сохраняет исторические расчеты: `ScenarioRun` неизменяем и
не удаляется вместе со сценарием.

## 3. Источники данных

### 3.1. Состояние

```bash
GET /api/v1/sources
GET /api/v1/sources/{id}/metrics
GET /api/v1/sources/{id}/confidence
```

Экран качества источников показывает: категорию, последний запуск,
успешность, latency, число предложений, ошибки, статус, доступный горизонт
и Source Confidence.

### 3.2. Управление

```bash
POST  /api/v1/sources/{id}/enable
POST  /api/v1/sources/{id}/disable
POST  /api/v1/sources/{id}/health-check
PATCH /api/v1/sources/{id}
```

Отключение источника вступает в силу со следующего снимка. Исторические
расчеты не пересчитываются.

### 3.3. Учетные данные

Секреты задаются **только через окружение**, никогда через API или БД:

| Источник | Переменные |
|---|---|
| Яндекс Путешествия | `YANDEX_TRAVEL_TOKEN` |
| TravelLine | `TRAVELLINE_CLIENT_ID`, `TRAVELLINE_CLIENT_SECRET` |

Источник, требующий учетных данных, при их отсутствии возвращает
`DISABLED` / `NOT_CONFIGURED`. Это штатное состояние, а не ошибка.

### 3.4. Предохранитель

После `CONNECTOR_CIRCUIT_BREAKER_FAILURES` подряд неуспешных обращений
источник временно исключается из сбора на
`CONNECTOR_CIRCUIT_BREAKER_COOLDOWN_SECONDS`. Состояние видно в поле
`circuit_open_until`. Принудительное закрытие — `POST .../enable`.

### 3.5. Квалификация

Перевод источника в `APPROVED` — явное решение администратора, а не
автоматика: автоматическая квалификация исказила бы смысл go/no-go.
Результаты проверки — в [SOURCE_QUALIFICATION.md](SOURCE_QUALIFICATION.md).

## 4. Профили расчета

### 4.1. Жизненный цикл

```
DRAFT  →  ACTIVE  →  ARCHIVED
```

- Одновременно активна **одна** версия профиля на `code`.
- `ACTIVE`-версия **неизменяема**. Изменение правил создает новую версию.
- Старые `ScenarioRun` при смене версии **не пересчитываются**.

```bash
GET  /api/v1/calculation-profiles
POST /api/v1/calculation-profiles                  # создать черновик
POST /api/v1/calculation-profiles/{id}/clone       # склонировать под правку
POST /api/v1/calculation-profiles/{id}/activate
POST /api/v1/calculation-profiles/{id}/archive
```

### 4.2. Поставляемые профили

| Профиль | Назначение |
|---|---|
| `baseline` | Продуктивная методика. Синтетические источники запрещены |
| `sandbox` | Прогон конвейера без внешней сети. Допускает песочницу. **Не для управленческих выводов** |

### 4.3. Что настраивается

Все пороги методики вынесены в профиль: фильтры, допуск источника,
параметры выбросов, правила агрегации, веса Quality Score, пороги
Scenario Confidence, лимиты времени, правила пересчета транспортных цен.
Полное описание — в [методике расчета](CALCULATION_METHODOLOGY.md).

Изменение любого порога требует новой версии профиля и последующей проверки
на challenge set.

### 4.4. Сравнение методик

Правильный способ сравнить две методики — пересчитать **один и тот же
снимок** разными профилями:

```bash
POST /api/v1/market-snapshots/{snapshot_id}/recalculate
{ "profile_id": "<uuid>" }
```

Исходный снимок не меняется, создается новый `ScenarioRun`. Так исключается
влияние различий в собранных данных.

## 5. Задачи и повторные запуски

```bash
GET  /api/v1/jobs?status=FAILED
GET  /api/v1/jobs/{id}
GET  /api/v1/jobs/{id}/events
POST /api/v1/jobs/{id}/retry
POST /api/v1/jobs/{id}/cancel
```

Повторный запуск идемпотентен: в пределах одного временного окна он не
создаст дублирующий `MarketSnapshot`, если не запрошено принудительное
обновление.

Ручной прогон мониторинга:

```bash
POST /api/v1/admin/monitoring/run                         # весь каталог
POST /api/v1/admin/monitoring/scenarios/{id}/run          # один сценарий
```

## 6. Кэш результатов

TTL по умолчанию — 45 минут, настраивается в профиле
(`limits.result_cache_ttl_minutes`) и переменной `RESULT_CACHE_TTL_MINUTES`.

Принудительное обновление конкретного расчета — параметр `force_refresh`
при запуске расчета. Полная очистка кэша — задача
`tco.maintenance.purge_result_cache`.

Redis используется как быстрый слой; источником истины остается таблица в
PostgreSQL. При недоступности Redis кэш продолжает работать на БД.

## 7. Retention

| Данные | Срок по умолчанию | Переменная |
|---|---:|---|
| Метаданные `MarketSnapshot` | бессрочно | `RETENTION_SNAPSHOT_METADATA_DAYS` |
| `ScenarioRun` | бессрочно | `RETENTION_RUN_DAYS` |
| Нормализованные предложения | 90 дней | `RETENTION_OFFERS_DAYS` |
| Сырые ответы API | 45 дней | `RETENTION_RAW_DAYS` |
| HTML-снимки | 45 дней | `RETENTION_HTML_DAYS` |
| Файлы экспорта | 7 дней | `RETENTION_EXPORT_DAYS` |

`0` означает «бессрочно».

После очистки предложений снимок помечается `offers_purged_at` и **больше не
может быть пересчитан** — остаются только метаданные и агрегаты. Это
осознанный компромисс между глубиной аудита и объемом хранилища.

## 8. Приемочная проверка методики

```bash
python scripts/run_challenge_set.py --profile baseline
```

Скрипт прогоняет 30 контрольных сценариев и формирует
`docs/CHALLENGE_SET_RESULTS.md` с вердиктами:

| Вердикт | Значение |
|---|---|
| `PASS` | Поведение соответствует ожидаемому |
| `ATTENTION` | Отклонение, объяснимое состоянием рынка: требует взгляда аналитика |
| `FAIL` | Нарушение обязательного правила методики — дефект |

Ненулевой код возврата означает наличие `FAIL`.
