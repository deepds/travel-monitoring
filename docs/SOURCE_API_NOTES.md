# Особенности API источников

Свод отклонений, ограничений и подводных камней двух рабочих источников —
Туту (MCP) и РЖД. Здесь только то, что **проверено на живом сервисе** и что
нельзя вывести из публичного описания: именно эти детали ломают расчет молча,
без ошибки, если о них не знать.

Формат записи: факт → следствие для методики → как обходим.

Последняя проверка: **2026-08-04**.

Смежные документы: [DATA_CONTRACT.md](DATA_CONTRACT.md) — что мы храним,
[CALCULATION_METHODOLOGY.md](CALCULATION_METHODOLOGY.md) — как считаем.

---

## Сводка: что каждый источник умеет

| | Туту (`tutu_mcp`) | РЖД (`rzd`) |
|---|---|---|
| Протокол | MCP (JSON-RPC поверх HTTP + SSE) | REST, двухфазный |
| Хост | `mcp.tutu.ru` | `ticket.rzd.ru` |
| Авторизация | не требуется | не требуется |
| Авиа | да | нет |
| ЖД | да, но класс вагона — только вторым вызовом | да, класс сразу |
| Проживание | да | нет |
| Цена | предкорзинная в карте мест, корзинная в поиске | тариф перевозчика |

Пересечение ровно одно — **ЖД**. Это единственное место, где два источника
можно сопоставить, и единственное, где расхождение цен осмысленно.

## Туту (MCP)

### Имена аргументов не зафиксированы

Публичное описание инструментов и фактическая схема расходятся, а схема
меняется между версиями сервера. Поэтому коннектор читает JSON-схему
инструмента во время выполнения и подбирает имя аргумента из списка кандидатов
(`ARG_ALIASES` в [tutu_mcp.py](../tco/connectors/tutu_mcp.py)).

**Следствие:** жестко зашитое имя аргумента однажды перестанет работать без
всякой ошибки — параметр просто проигнорируется, и выдача будет по другому
запросу.

**Обход:** любое новое поле добавлять в `ARG_ALIASES`, а не в вызов.

### Поиск ЖД не принимает обратную дату

В схеме `search_rail` нет аргумента для даты возврата: только
`origin`, `destination`, `departure_date`, `passengers`, `sort`, `view`,
`page`, `page_size`, `direct_only`, `price_max`, `carriers`, `from_city`, `to_city`.

**Следствие:** round-trip собирается из двух односторонних поисков и
перемножения плеч. Число комбинаций ограничено (`roundtrip_legs_per_direction`),
иначе выборка раздувается квадратично.

### Поиск ЖД не содержит класса вагона вообще

Проверено по полной структуре сырого ответа: ни `car_type`, ни `coach_type`,
ни `service_class` — ни под каким именем. Есть только агрегат по тарифам:

```json
"fares": {"count": 27, "price_from": 1623.32, "price_to": 11233.24,
          "currency": "RUB", "refundable_count": 19, "changeable_count": 0}
```

А `offer.price.amount` равен `fares.price_from` — то есть **минимуму по всем
классам сразу**, от сидячего до СВ.

**Следствие, критическое:** пока класс неизвестен, предложение Туту
несопоставимо ни с РЖД, ни с методикой (плацкарт и купе агрегируются
раздельно). До 2026-08-04 все ЖД-предложения Туту отбрасывались с
`PROFILE_FILTER / RAIL_CLASS_UNCLASSIFIED`, и ЖД-стоимость считалась по
одному источнику при формально двух подключенных.

**Нельзя обходить так:** подставлять класс из сценария или убирать класс из
ключа эквивалентности. Оба варианта дают не «меньше данных», а неверные числа:
цена сидячего места встанет в одну строку с купе.

### `get_offer_details` обрезает список тарифов двадцатью строками

`variants[]` возвращается отсортированным по возрастанию цены и жестко
ограничен 20 строками; `view='full'` этого не меняет, пагинации нет.

**Следствие:** на поезде с большим числом плацкартных тарифов купе в
`variants[]` не попадает вовсе. Пример — поезд 587М Москва → Сочи:
`fares.count` = 60, вернулось 20 строк, все плацкартные, хотя в составе есть
купейные и люксовые вагоны.

**Обход:** класс и цену брать из `get_rail_seatmap`, а не из
`get_offer_details`.

### `get_rail_seatmap` — рабочий источник цены по классу

Один вызов на поезд возвращает `cars[]` со всеми вагонами состава, у каждого
`car_type` и `seat_groups[]`, где лежит `cheapest_fare.price.amount`.

```
542М: {RESERVED_SEAT: 4621.4, COMPARTMENT: 4791.5}
304М: {RESERVED_SEAT: 4621.4, COMPARTMENT: 6890.8}
587М: {RESERVED_SEAT: 4621.4, COMPARTMENT: 4791.5, LUX: 19347.1}
```

Ограничения вызова: `max_cars` ≤ **20** (сервер отвечает ошибкой валидации на
большее), `max_seats_per_car` можно ставить в 1 — сами места не нужны, группы
с ценами приходят полностью.

`seatmap_status` бывает `ok` и `no_layout_for_carrier` — второе означает
«перевозчик не отдает схему», а **не** «мест нет». Обрабатывается как отсутствие
данных, не как сбой.

### Тип вагона Туту уже нормализован

`car_type` приходит значениями `RESERVED_SEAT`, `COMPARTMENT`, `LUX`,
`SEDENTARY` — они совпадают с `RailClass`, поэтому таблица соответствия не
нужна.

**Важно:** выводить класс из кода обслуживания (`3Б`, `2К`, `1Л`) по первому
символу **нельзя** — `2В` и `2С` это сидячие вагоны, а не купе. Если Туту
однажды перестанет отдавать `car_type`, правильный источник — `service_packages`
в `train_vehicle`, где классы сгруппированы по названиям:

```json
[{"name": "Плацкарт", "service_classes": ["3Б","3Д","3Т","3Э"]},
 {"name": "Купе",     "service_classes": ["2К","2У","2Ш"]},
 {"name": "СВ",       "service_classes": ["1Л"]}]
```

### Цены карты мест предкорзинные — ниже итоговых на 6–8 %

Прямая цитата из `pricing_note` ответа: цены в группах мест — это
«pre-cart totals (fare + its service fee)», а на оформлении Туту добавляет
собственный, больший сервисный сбор. Цены же **листинга поиска соответствуют
корзине**.

**Следствие:** цена по классу (из карты мест) и цена «от» (из поиска) — из
разных ценовых баз. Сравнение Туту с РЖД по классу систематически занижает
Туту на несколько процентов.

**Как поступаем:** берем цену карты мест как есть, без поправочного
коэффициента — домножать чужую цену на свою оценку значило бы выдавать
предположение за наблюдение. Провенанс сохраняется в `source_metadata`
предложения (`price_source: seatmap | search`), чтобы расхождение можно было
объяснить, а не гадать.

### Цена — за одного пассажира

Проверено сравнением вызовов с `passengers=1` и `passengers=2`: цены в
`variants[]` и `seat_groups[]` не меняются.

**Следствие:** `price_basis = PER_PASSENGER`, домножение на состав делает
нормализация, как и для РЖД.

### Ограничения размера выдачи

`page_size` больше **30** сервер молча ужимает до 30 (коннектор логирует
«Аргумент приведен к границам схемы инструмента»). `max_cars` карты мест ≤ 20.

**Следствие:** одним поиском больше 30 поездов не получить; глубже — только
через `page`.

### Стоимость сбора по времени

Один сбор ЖД по маршруту — это поиск на каждое направление плюс вызов карты
мест на каждый детализируемый поезд. Замер на живом сервисе:
**~20 с и 108 предложений** на маршрут Москва → Сочи при бюджете 16 карт мест.

**Следствие:** бюджет вызовов ограничен (`rail_seatmap_calls`, по умолчанию 16
на оба направления). Без ограничения сбор по каталогу из сотни сценариев
становится неприемлемо долгим.

### Прочее по Туту

- **Цена авиа** лежит в `price.amount`, плечи — в `legs[]` с меткой
  `outbound`/`inbound`; пункты приходят строками вида
  `«Москва — Внуково (VKO)»`, а не объектами.
- **Каждый тарифный вариант авиа — отдельное предложение:** у вариантов разные
  цена и багаж, схлопывание потеряло бы именно то, чем методика различает
  авиатарифы.
- **Города** могут требоваться как идентификатор, а не строка — коннектор
  разрешает название через геопоиск и подставляет то, что ждет схема.
- **Сортировка по умолчанию** `price_asc` — первым идет самый дешевый, часто
  медленный поезд, а не скоростной.

## РЖД

### Публичный путь цен не работает

`/api/v1/railway-service/prices/train-pricing` устойчиво отвечает
`500 INTERNAL_ERROR` на любой формат тела.

**Обход:** используется B2B-путь `/apib2b/p/Railway/V1/Search/TrainPricing`
с параметром `service_provider=B2B_RZD`. Он отвечает полноценной выдачей и,
что важно при отладке, **сам называет некорректные поля** в тексте ошибки.

### Двухфазный протокол RID

Первый запрос может вернуть `result: "RID"` и идентификатор `RID`. Ответ с
данными приходит только при повторном опросе того же endpoint с этим `RID` —
и не сразу.

**Следствие:** сбор по РЖД принципиально медленнее одного HTTP-запроса.
Коннектор опрашивает до 6 раз с нарастающей паузой (до 2.5 с).

**Подвох:** если не дождаться `result: OK` и разобрать промежуточный ответ,
получится пустая выдача без признака ошибки.

### Имена полей запроса подсказывает сам сервис

Поле даты называется `DepartureDate` — это выяснено из текста ошибки
«Параметр 'request.DepartureDate' должен быть задан». Тот же прием работает
для остальных полей.

### Форма ответа плавает

Поезда приходят либо в `Trains`, либо вложенно в `Tp[].List`. Вагоны — либо
`CarGroups`, либо `Cars`. Имена полей внутри тоже дублируются:
`TrainNumber` / `DisplayTrainNumber`, `DepartureDateTime` /
`LocalDepartureDateTime`, `MinPrice` / `Price`.

**Обход:** каждое поле читается по списку кандидатов; неизвестная форма дает
пустой список, а не исключение.

### Что отбрасывается на стороне коннектора

- `IsSaleForbidden = true` — и на уровне поезда, и на уровне группы вагонов.
- Классы вне методики: **люкс, СВ и сидячие** не проходят `CAR_TYPE_MAP` и
  отбрасываются. Остаются только плацкарт и купе.
- Группы без цены.

**Следствие:** число предложений РЖД в снимке заметно меньше, чем поездов в
выдаче, и это ожидаемо, а не потеря данных.

### Прочее по РЖД

- `TripDuration` приходит **числом минут** (`521.0`), а не строкой времени.
- Коды станций разрешаются через `/api/v1/suggests` и кэшируются в пределах
  вызова; для города можно задать код явно в справочнике.
- Цена — **за одного пассажира** за плечо (`price_basis = PER_PASSENGER`),
  итог собирается как `(туда + обратно) × число пассажиров`.

## Наблюдаемый разрыв цен между источниками

Замер на живом расчёте Краснодар → Москва, купе, 2 взрослых (2026-08-05):

```
медиана РЖД     17 611 ₽      предложений 20
медиана Туту    26 881 ₽      предложений 32
итог расчёта    22 246 ₽      = среднее двух медиан
```

Поштучное сравнение по одним и тем же поездам даёт разрыв **11–45 %**,
медиана разрыва — **32 %**:

```
472С↔471М купе:  РЖД 16 998 | Туту 18 951   (+11.5 %)
286С↔113М купе:  РЖД 17 377 | Туту 23 475   (+35.1 %)
114Э↔113М купе:  РЖД 17 403 | Туту 25 239   (+45.0 %)
```

Три вывода, которые важно не перепутать:

1. **Разрыв реален и объясним:** РЖД отдаёт тариф перевозчика, Туту — цену
   агента со своим сбором. Причём цена Туту предкорзинная, то есть настоящий
   разрыв ещё больше.
2. **Межисточниковое расхождение в расчёте (42 %) выше поштучного (32 %)**,
   потому что медианы считаются по разным корзинам: Туту возвращает больше
   комбинаций поездов, чем РЖД. Поштучное сравнение — честный вид, расхождение
   медиан включает ещё и разницу составов выдачи.
3. **ЖД-стоимость вырастет примерно на четверть** по сравнению с тем, что
   показывал стенд раньше. Это не регресс: до 2026-08-05 ЖД считался по одному
   РЖД, потому что предложения Туту отбрасывались, и цифра была занижена
   относительно методики, которая предписывает усреднять два источника.

## Что из этого следует для сравнения источников

1. Сопоставление идет по ключу эквивалентности: тип, номера поездов туда и
   обратно, даты, класс вагона — **без источника и без цены**. Поэтому
   заполненный класс у обеих сторон обязателен, иначе групп не будет вовсе.
2. Плацкарт и купе не смешиваются никогда — ни в расчете, ни в сравнении.
3. Расхождение цен между Туту и РЖД **ожидаемо и осмысленно**: один источник
   агент со своей наценкой, второй перевозчик. Но к нему примешана
   предкорзинная скидка карты мест — при трактовке разницы это надо помнить.
4. Люкс, СВ и сидячие вагоны вне методики у обоих источников. Если они
   появятся в выдаче, они не попадут ни в медиану, ни в сравнение.
