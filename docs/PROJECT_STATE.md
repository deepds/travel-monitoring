## 3. Дефекты, найденные и устраненные

Все обнаружены только на живых источниках — на синтетике они не
воспроизводились.

| Дефект | Проявление | Исправление |
|---|---|---|
| `page_size=50` при максимуме 30 | Туту отклонял все запросы на валидации | Числовые аргументы зажимаются в границы схемы инструмента |
| Неверный контракт разбора Туту | Ноль предложений или падение `'str' object has no attribute 'get'` | Парсеры переписаны под фактический ответ |
| Нерабочий эндпоинт РЖД | `500 INTERNAL_ERROR` на любой запрос цен | Переход на B2B-путь, поле `DepartureDate` |
| Метка обратного плеча | Все 108 авиапредложений в `INVALID_ROUTE` | Источник использует `return`, а не `inbound` |
| Фильтры отелей не доходили до источника | Из 30 объектов 22 отсеивались профилем | Реальный параметр `stars`, а не `stars_min`/`stars_max` |
| `force_refresh` ломал сбор | Нарушение уникального индекса снимка | Ключ идемпотентности получает соль |
| Ограничитель темпа не применялся | Поле хранилось, но при сборе игнорировалось | Token bucket в Redis с деградацией на локальный |
| **`stars` отправлялся строкой** | **143 из 176 запросов проживания отклонялись: схема ждет массив категорий** | **Приведение к объявленному типу вынесено в `_coerce`: коннектор читает схему, значит соблюдает и типы, а не только границы** |
| **Неудача одного типа снимала весь источник** | **Сломанный поиск отелей обнулял 9 142 собранных авиапредложения того же источника** | **Разрез по типам в `SourceCollectionInfo.by_offer_type`, допуск компонента считается через `scoped_to`** |
| **Питание не запрашивалось для «без питания»** | **513 предложений в `MEAL_MISMATCH`: источник умеет фильтровать, но план в выдаче не возвращает** | **Передается аргумент `meals`, запрошенный план подтверждается фактом серверной фильтрации** |

## 4. Управление каталогом сценариев

Каталог задается двумя способами: файлом (`POST /admin/scenarios/import`,
CSV или YAML) и вручную из интерфейса. Ручной путь добавлен 2026-08-04:
раньше, чтобы завести один маршрут, приходилось править файл и перезаливать
каталог целиком.

### Создание

Кнопка «Создать сценарий» есть в каталоге сценариев и на экране
администрирования — обе открывают один диалог. Конструктор **управляемый**:
значения приходят из справочников `/reference/*`, даты выбираются календарем и
ограничены горизонтом источников. Свободного ввода нет намеренно — сценарий с
неподдерживаемым параметром не дошел бы до источников, а выяснилось бы это
только на первом сборе.

Отпечаток сценария стабилен, поэтому повтор тех же параметров **не создает
дубль**: API отвечает `200` с `created: false` и возвращает существующую
запись, интерфейс об этом сообщает. Создание доступно роли `ANALYST` и выше,
изменение статуса и удаление — только `ADMIN`.

### Состав сценария

Компонент можно не наблюдать: в конструкторе у «Транспорта» и «Размещения»
есть вариант «Нет». Хотя бы один обязан остаться. Ненаблюдаемый компонент не
считается недостающим — сценарий «только перелет» дает статус `SUCCESS`,
полноценный итог и не теряет 30 % оценки качества. Подробности и границы —
в [методике §17](CALCULATION_METHODOLOGY.md).

Итог односоставного сценария не сопоставим с итогом полного, и интерфейс
предупреждает об этом при создании.

### Наблюдение

Признак `is_active` управляет попаданием в ежечасный плановый сбор.
Переключатель есть и в списке, и в карточке; карточка выключенного сценария
явно предупреждает, что данные по нему не собираются, а накопленное
сохраняется. Сценарий автоматически деактивируется после `active_until` —
это делает `deactivate_finished_scenarios` в цикле обслуживания.

### Удаление: два разных режима

| Режим | Запрос | Что происходит |
|---|---|---|
| Запись каталога | `DELETE /scenarios/{id}` | Сценарий скрыт и снят с наблюдения; снимки, расчеты и предложения остаются |
| Вместе с данными | `DELETE /scenarios/{id}?purge_data=true` | Снимки, расчеты, предложения и сохраненные ответы источников уничтожаются, запись удаляется физически |

Режим по умолчанию — мягкий, и это осознанно: снимки рынка относятся к
прошлому, их достоверность не зависит от того, наблюдаем ли мы маршрут дальше.
Полное удаление безвозвратно, поэтому интерфейс запрашивает
`GET /scenarios/{id}/footprint` **до** открытия диалога и показывает числами,
что именно будет уничтожено.

Переживают полное удаление и не должны удаляться вместе со сценарием:

- **записи аудита** — иначе теряется след самого удаления;
- **журнал задач** — операционная история, обнуляется только ссылка;
- **технические метрики источников** — описывают поведение источника, а не
  маршрут; их потеря исказила бы историю Source Confidence.

Порядок удаления продиктован внешними ключами и зафиксирован в
`tco/services/scenario_lifecycle.py`. Важная тонкость, на которой первая
версия падала: у предложений и у метрик источника есть **собственная** ссылка
на сценарий помимо ссылки на снимок, поэтому каскада снимка недостаточно.

## 6. Что делать при продолжении

Порядок по приоритету:

1. **Разобрать 66 расчетов `PARTIAL_SUCCESS`** — в них есть проживание, но нет
   транспорта. Метод тот же, что дал результат в разделе 3: смотреть воронку
   по `exclusion_reason` и `ineligibility_reasons`, отличая дефект от
   штатной фильтрации.
   ```sql
   SELECT exclusion_reason, left(exclusion_detail, 60), count(*)
   FROM offers WHERE offer_type IN ('FLIGHT','RAIL') GROUP BY 1,2 ORDER BY 3 DESC;
   ```

2. **Прогнать challenge set на реальных источниках** — после исправлений он не
   перезапускался:
   ```bash
   python scripts/run_challenge_set.py --profile baseline
   ```
   Результат ложится в `docs/CHALLENGE_SET_RESULTS.md`.

3. **Получить второй источник проживания.** Единственный невыполненный пункт
   Definition of Done. Коннекторы готовы и включаются автоматически при
   появлении `YANDEX_TRAVEL_TOKEN` либо `TRAVELLINE_CLIENT_*`. Пока источник
   один, компонента проживания всегда `COMPLETE_SINGLE_SOURCE`, а Scenario
   Confidence не может подняться до `HIGH`.

4. **Откалибровать пороги** методики на накопленных данных: допуск источника,
   веса Quality Score, границы Scenario Confidence. Данных для этого стало
   достаточно.

5. **Замерить производительность** на полном каталоге и провести учебное
   восстановление из резервной копии.

6. **Разобрать класс вагона у Туту** — все 256 ЖД-предложений источника уходят
   в `RAIL_CLASS_UNCLASSIFIED`. Не срочно: направление закрывает РЖД, но это
   потерянный второй источник для транспорта.

## 7. Чего делать нельзя

- **`docker compose down -v` на стенде с данными.** Ключ `-v` удаляет тома.
  Наблюдения невосполнимы: источники не отдают историю цен. Для обновления
  есть `scripts/deploy.sh`, для остановки — `docker compose stop`.
- **Включать песочницу, не вернув метки в интерфейс.** Признак
  `contains_synthetic_data` сохранен в модели и API, но с экранов убран
  2026-08-04: источники дают реальные данные, а плашки были шумом. Профиль
  `baseline` синтетику не допускает, дашборд отсекает ее фильтром — поэтому
  сейчас это безопасно. Если песочницу когда-нибудь включат, метки придется
  вернуть: иначе ее данные станут неотличимы от рыночных.
- **Называть показатель средним чеком.** Система считает расчетную типовую
  стоимость по предложениям, а не по транзакциям.
- **Править методику в активной версии профиля.** Активная версия неизменяема;
  изменение оформляется новой версией, иначе исторические расчеты теряют
  привязку к правилам, по которым были получены.
- **Удалять сценарий с `purge_data=true` «чтобы прибрать каталог».** Это
  уничтожает историю наблюдений по маршруту, а не только запись. Ошибочно
  заведенный сценарий без данных — единственный безопасный случай; во всех
  остальных достаточно мягкого удаления, оно тоже снимает сценарий с
  наблюдения (§4).
